## Context

`GoogleBooks.search(query, page)` (`src/app/book-search/google-books.ts`) currently builds its query as either `isbn:<digits>` or the raw search text, and always attaches `langRestrict` from the current `Language`. `BookCard` (`src/app/book-card/book-card.ts`) renders the full attribute set (title, authors, publisher, date, description, rating, price) and is used both on the search page and the cart page. `CartPage` (`src/app/cart-page/cart-page.ts`) reads `Cart.books()` directly. See proposal.md for what's being added and why.

## Goals / Non-Goals

**Goals:**
- One Google Books request per recommendation fetch, regardless of how many distinct authors are in the cart (up to the 5-author cap).
- A minimal card component, visually consistent with `BookCard`'s existing icon-button styling, but with a much smaller field set.
- Client-side windowed paging with no new fetches per page turn.
- Refetching only when it would actually change the results (the cart's unique-author set), not on every cart mutation.

**Non-Goals:**
- No persistence of "already recommended" or "dismissed" state — recommendations are recomputed fresh from the current cart each time the author set changes.
- No stable book identity (volume ID) — exclusion is a best-effort title match, same data-model limitation the rest of the app already lives with (e.g. `Cart.remove()` matches by object reference, not ID).
- No changes to `BookCard`, `Cart`, or the existing search page's pagination.

## Decisions

- **New `GoogleBooks.searchByAuthors(authors: string[]): Observable<SearchResultsPage>`**: builds `q` as `inauthor:"A" OR inauthor:"B" OR ...` (each author quoted to keep multi-word names intact), reusing the existing `toBookSummary()` mapping and `langRestrict` attachment — same response shape as `search()`, so the rest of the pipeline (mapping, price generation) is untouched. Takes the already-capped (≤5) author list; the caller does the capping, not this method, keeping it a thin query-builder.
- **New `BookRecommendations` component** (`src/app/book-recommendations/`), owning the fetch, the author-set-change detection, and the paging window. Takes the cart's books as input (or injects `Cart` directly, matching how `CartPage` already injects it — simpler, no new prop-drilling). Computes `uniqueAuthors = computed(() => [...new Set(cart.books().flatMap(b => b.authors ?? []))].slice(0, 5))`, and a constructor `effect()` that refetches only when this computed's *value* changes — using an explicit previous-value comparison (join into a string and compare) rather than relying on Angular's default reference equality for arrays, since a new array instance is created on every recompute even when its contents are identical.
- **New `RecommendationCard` component** (`src/app/recommendation-card/`), not a `BookCard` variant: cover image (`@if (book().coverImageUrl)`, same as `BookCard`), title, authors joined with `, ` (same join `BookCard` already uses), and an add-to-cart button reusing the exact same cart-icon SVG markup `BookCard`'s `.add-to-cart-button` uses, for visual consistency with the "Cart action controls use consistent icon-based buttons" requirement already governing `BookCard`'s and `CartPage`'s icon buttons. Takes a `book = input.required<BookSummary>()`, injects `Cart` and `GoogleAuth` the same way `BookCard` does (add-to-cart only shown when signed in, matching existing behavior) and `Language` for the accessible label.
- **Exclusion matching**: `cart.books().some(b => b.title?.trim().toLowerCase() === candidate.title?.trim().toLowerCase())` — case-insensitive, whitespace-trimmed title comparison, applied client-side after the fetch returns (simpler than trying to exclude via the query itself, which Google Books' query language doesn't support well for a NOT-title-equals condition).
- **Paging**: a `pageIndex` signal and a `PAGE_SIZE` constant (4, matching a typical card-row width); `visibleBooks = computed(() => allRecommendations().slice(pageIndex() * PAGE_SIZE, (pageIndex() + 1) * PAGE_SIZE))`, `hasPrevious`/`hasNext` computeds — same interaction pattern as `book-search.html`'s pagination, but flipping through an already-fetched in-memory array instead of calling the API per page.
- **Section title**: new `cartPage.recommendationsHeading` translation key ("More books by these authors" / "Weitere Bücher dieser Autoren"), rendered as an `<h2>` (the cart page's own title is already an `<h1>`).
- **Revision — placement, cross-card alignment, side arrows, full width**: four follow-up layout adjustments. (1) The section moved from after the payment section to before it, both still satisfying the spec's "below the cart's book list" wording. (2) Card alignment: `.recommendation-title`/`.recommendation-authors` reserve fixed `min-height`s (2 lines / 1 line) so shorter content doesn't shift things up, the cover is wrapped in an always-present `.recommendation-cover-slot` (fixed height, empty when no image — no placeholder graphic, just reserved space) so a missing cover doesn't shift the card's content either, and the add-to-cart button uses `margin-top: auto` to sit flush at the bottom of each card — which the row's default `align-items: stretch` equalizes in height. (3) The bottom-centered text Previous/Next became a `.recommendations-row` with icon-only chevron arrows flanking the card list on each side (`aria-label` carries the same translated text that used to be visible), vertically centered rather than stretched to the row's full height — matching a common carousel convention while keeping the arrows compact so they don't eat into the cards' width. (4) `RecommendationCard`'s fixed `width: 9rem` became `flex: 1 1 0` (with a `max-width` cap), so the cards themselves stretch to fill the same content width as the book list and payment section, rather than clustering at a fixed size with empty space alongside.
- **Revision — smaller cover, side-by-side layout, price, text truncation**: `RecommendationCard` switched from a vertical layout (cover on top, details below) to a horizontal one: `.recommendation-cover-slot` shrank from a fixed `9rem` to a fixed `4.5rem` square, `align-self: center`'d against the card's row, and a new `.recommendation-details` wrapper (a flex column, `flex: 1`) holds the title, authors, a new price line, and the add-to-cart button to its right. Price reuses `BookCard`'s exact formatting (`price.toLocaleString(language.localeCode(), { style: 'currency', currency: 'EUR' })`), with no label, mirroring how `BookCard` shows it. The card's `max-width` grew from `14rem` to `20rem` to give the now-wider side-by-side content room. The existing cross-card alignment technique (fixed-height title/authors, `margin-top: auto` on the button, the row's `align-items: stretch`) still holds: `.recommendation-details` stretches to fill the card's full height (set by the tallest card in `.recommendations-list`), so the button lands at the same Y position across every card regardless of content length or a missing cover. Title and author text longer than 50 characters is hard-cut (no word-boundary awareness, unlike `BookCard`'s longer description truncation) and appended with `…`, computed in the component (`displayTitle`/`displayAuthors`) rather than via CSS, since the character limit is exact rather than a layout-driven line clamp.
- **Revision — top-aligned cover, tighter title/author spacing, responsive wrapping**: three follow-up fixes. (1) `.recommendation-cover-slot`'s `align-self` changed from `center` to `flex-start`, so the cover sits flush with the top of the card (aligned with the title) instead of vertically centered against the taller details column. (2) `.recommendation-details` dropped its uniform `gap` in favor of per-element margins: `.recommendation-authors` now has `margin-top: 0.125rem` (tight, down from the prior `0.25rem` gap) while `.recommendation-price` keeps a normal `margin-top: 0.375rem`, so only the title-author spacing tightened. (3) The card row wasn't responsive: at narrow viewports the four fixed-content cards (plus `white-space: nowrap` authors text) overflowed `.recommendations-row` horizontally with `flex-wrap` never set, pushing the Next arrow off-screen since the row relies on arrows instead of a scrollbar. Fixed by giving `.recommendations-list` `flex-wrap: wrap` and `min-width: 0` (so it can shrink within the row instead of forcing the row wider), and changing each card's sizing from `flex: 1 1 0; min-width: 0` to `flex: 1 1 12rem; min-width: 12rem`, so cards wrap onto additional lines instead of shrinking to unreadable widths or overflowing — the arrows stay vertically centered against the row's full (now possibly multi-line) height via the existing `align-items: center` on `.recommendations-row`, so they remain visible and clickable at any width.
- **Revision — single row only, actually tight title/author gap**: the wrap-based responsiveness fix from the prior revision was rejected: wrapping into two lines of cards was not wanted. Reverted `.recommendations-list` to `flex-wrap`'s default (`nowrap`) and each card's sizing back to `flex: 1 1 0; min-width: 0`, so the four cards always render in a single row, shrinking as needed rather than wrapping. To let them shrink far enough to still fit without a horizontal scrollbar at narrow widths, `.recommendation-cover-slot` also became shrinkable: it now uses `flex-basis: 4.5rem` with `aspect-ratio: 1 / 1` and a `min-width: 2rem` floor (down from a rigid `flex-shrink: 0; width: 4.5rem; height: 4.5rem`), so the cover scales down proportionally alongside the text instead of staying a fixed size that the row couldn't accommodate. Separately, the "still too big" title/author gap turned out not to be the `0.125rem` margin (already small) but `.recommendation-title`'s `min-height: calc(line-height * 2em)` — a fixed two-line reservation added in an earlier revision for cross-card alignment, which left a full blank line of empty space under any title short enough to fit on one line. Removed that `min-height` (and the matching one on `.recommendation-authors`), keeping only `-webkit-line-clamp: 2` to cap overflow; the title/authors block now hugs its actual content, so the visible gap is exactly the `0.125rem` margin. This trades away perfect authors/price Y-alignment across cards with differing title line counts (title/authors/price can now sit at different heights per card) in favor of natural, tight spacing; the add-to-cart button's Y-position stays aligned regardless, since it's still pinned via `margin-top: auto` against the card's full stretched height.
- **Revision — page size reduced from 4 to 3**: `PAGE_SIZE` in `book-recommendations.ts` changed from `4` to `3`, so each page of the windowed paging (design decision above) shows 3 cards instead of 4. No other paging logic changed — `visibleRecommendations`, `hasPreviousPage`/`hasNextPage`, and `hasMultiplePages` all derive from the same constant, so this is a one-line change. Also gives the single-row-only layout (prior revision) more per-card width to work with before shrinking kicks in.
- **Revision — slightly larger price-to-button gap**: `.recommendation-price` gained a `margin-bottom: 0.375rem` (previously `0`, matching its existing `margin-top`). The add-to-cart button is still pinned to the card's bottom via `margin-top: auto` (needed for cross-card alignment), so a margin directly on the button wouldn't reliably add visible space — `margin-top: auto` already claims all remaining room. Adding the gap to the price's own `margin-bottom` instead guarantees a minimum gap regardless of how much extra height the auto-margin ends up filling, since flexbox does not collapse margins between siblings.
- **Revision — bug fix: multi-author recommendations returned nothing**: the original `searchByAuthors` decision above (`q = inauthor:"A" OR inauthor:"B" OR ...`) was based on an incorrect assumption about the Google Books API. Verified directly against the live API: `inauthor:"Frank Herbert" OR inauthor:"Isaac Asimov"` returns either 0 results or a single irrelevant book unrelated to either author — the API does not reliably support OR-combining `inauthor:`-scoped clauses within one query, regardless of quoting, casing, or using `|` instead of `OR`. A single `inauthor:"X"` clause alone works correctly (hundreds of relevant results). This was never caught earlier because every unit/e2e test mocks the HTTP layer (so the query's real-world behavior was never exercised), and the one prior live-API manual verification (task 8.4) only ever had a single author in the cart, which happens to not trigger the OR-join path at all. Fixed by having `searchByAuthors` issue one request per author (via `forkJoin`) and merge the responses client-side, de-duplicating by title (case-insensitive, trimmed — same comparison style as the existing cart-exclusion filter) in case two authors' result sets overlap. This changes the "one request per fetch" quota characteristic to "up to `MAX_AUTHORS` (5) requests per fetch" — an unavoidable trade-off once the single-query approach is confirmed not to work; `MAX_AUTHORS` remains the cap on how large that can get. `BookRecommendations` needed no changes: it already just subscribes to `searchByAuthors(...)` and receives one merged `SearchResultsPage`, same as before.

## Risks / Trade-offs

- [Title-based exclusion can both under- and over-exclude — a genuinely different book that happens to share a title with a cart item gets excluded; a re-issued edition with a slightly different title slips through] → Accepted; there's no stable identifier available in this data model (same limitation the rest of the app already has), and the cost of either failure mode here is low (a recommendation list, not a correctness-critical path).
- [OR-joining many authors into one query can return a broad, loosely-relevant mix once several unrelated authors are represented in the cart] → Accepted as the direct trade-off for "one request, not N" per the user's explicit choice; the 5-author cap bounds how diluted it can get.
- [The author-set-change detection needs value comparison, not reference comparison, or it will refetch on every cart mutation regardless of whether the author set actually changed] → Addressed directly in the decision above (explicit string-join comparison); flagged here so it isn't quietly dropped during implementation.
