## Context

`BookSearch` (`src/app/book-search/book-search.ts`) holds a discriminated-union `SearchState`: `idle | loading | error | not-found | found`. The template (`book-search.html`) already branches on `state().kind` for each case. `GoogleBooks` (`src/app/book-search/google-books.ts`) has `search()` and `searchByAuthors()`, both built on a private `fetchVolumes(q, page)` that hardcodes `maxResults` to a module-level `PAGE_SIZE = 10` — there is no "give me N random books" capability today, and Google Books' API itself has no random endpoint. Every book's `price` is already a random value (10.00–70.50 €) generated once when the book is first mapped from the API response (`toBookSummary()`), and shown plainly everywhere else in the app — this change is the first place showing a fabricated discount on top of that. `BookRecommendations` (`src/app/book-recommendations/`) is the closest existing precedent for a self-contained section that injects its own dependencies and fetches its own data independently of its parent, and `RecommendationCard`'s single-row CSS (`flex-wrap` control) is the closest layout precedent, though that section also has Previous/Next arrows, which this one deliberately omits. The `theming` capability's "Interactive control feedback" requirement already establishes the pattern this reuses: disable motion under `prefers-reduced-motion`, but keep a non-motion visual cue rather than nothing at all. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- A self-contained `PromoSection` component that fetches its own random, cover-having books and needs no input from `BookSearch` beyond being mounted/unmounted.
- Reuse `GoogleBooks`'s existing request pipeline (`langRestrict`, API key attachment, `toBookSummary()` mapping) rather than building a parallel one.
- The "sale" the section advertises is honored all the way to the cart — activating "Add to cart" on a promo card charges the discounted price, not the original, so the joke pays off rather than reading as a bug.

**Non-Goals:**
- No true randomness from Google Books (no random endpoint exists) — "random" means a randomly chosen query from an AI-engineering-focused term pool, plus a large `maxResults` batch, client-side shuffled and filtered.
- No auto-rotating carousel — the fetched books are fixed for as long as the section stays mounted; a new random set is only drawn the next time the section is freshly mounted (see Decisions).
- No auto-rotating carousel, no pagination, no scrollbar — a card is either fully shown or not shown at all; see the visible-count decision below for how "fully shown" is now determined.

## Decisions

- **`GoogleBooks.searchRandom(): Observable<SearchResultsPage>`**: picks one query at random from a small curated pool of AI-engineering-related terms (e.g. `artificial intelligence`, `machine learning`, `deep learning`, `neural networks`, `large language models`, `generative AI`, `AI engineering`, `MLOps`, `natural language processing`, `computer vision`), and calls `fetchVolumes` with a large `maxResults` (e.g. 40, near the API's practical ceiling) to maximize the odds of finding enough cover-bearing results after filtering. `fetchVolumes` gains an optional `maxResults` parameter (defaulting to the existing `PAGE_SIZE` so `search()`/`searchByAuthors()` are unaffected) rather than a second near-duplicate method.
- **Cover-image filtering and sampling happen in `PromoSection`, not `GoogleBooks`**: `searchRandom()` returns whatever the API gives back (same shape as `search()`); `PromoSection` filters to `book.coverImageUrl !== undefined`, shuffles, and takes up to a generous cap (`MAX_PROMO_BOOKS = 20`) — not a fixed display count. This cap exists only to bound DOM size on absurdly wide screens; it is not the number of cards actually shown, which the row's CSS-overflow clipping (see below) determines from however many of these candidates fit at the current width. If fewer than the cap qualify, it shows however many do (down to 1); if zero qualify, the section renders nothing for that mount — the same "hidden when there's nothing to show" pattern `BookRecommendations` already uses, rather than showing a broken-looking partial section.
- **Mount/unmount drives the fetch, not an input flag**: `BookSearch` computes `showPromo = computed(() => state().kind === 'idle' || state().kind === 'not-found')` and the template does `@if (showPromo()) { <app-promo-section /> }`. `PromoSection` fetches once in its constructor with no `active` input or refetch-guard needed — Angular's own `@if` destroy/recreate cycle gives "fixed while shown, freshly re-randomized next time it's shown" for free, which is simpler than replicating `BookRecommendations`' author-set-comparison guard for a case that doesn't need it (there's no equivalent "did the meaningful input actually change" question here — every fresh mount should just re-roll).
- **Discount math**: for each fetched book, `PromoCard` computes a random discount percentage in the 40–90% range (rounded to a whole number for the badge, e.g. "-63%") once per card instance, and derives `nowPrice = round(book().price * (1 - percent/100), 2)`. `book().price` itself (the existing random 10.00–70.50 € value) is displayed struck through as the "original" price, unmodified.
- **The cart charges the discounted price**: `PromoCard`'s add-to-cart handler calls `cart.add({ ...book(), price: nowPrice })`, not `cart.add(book())`. This is a deliberate deviation from every other add-to-cart call site in the app (which always pass the book through unmodified) — the discount is fake, but once "purchased" it behaves like a real one, which is the more satisfying (and more honest, in its own backwards way) version of the joke than silently charging full price after showing a huge fake discount.
- **New components**: `PromoSection` (`src/app/promo-section/`, selector `app-promo-section`) owns the fetch, filtering, and sampling; `PromoCard` (`src/app/promo-card/`, selector `app-promo-card`) owns the per-book discount math and rendering. Neither extends or wraps `BookCard`/`RecommendationCard` — the explicit ask was a visually distinct, less-detailed card, and forcing shared inheritance onto genuinely different presentation would fight the design rather than help it.
- **Single-row layout, no partially-visible cards — JS-measured, superseding the earlier CSS-only approach**: `.promo-row { display: flex; flex-wrap: nowrap; overflow: hidden; }` still exists as a safety-net clip, but every fetched `PromoCard` (up to `MAX_PROMO_BOOKS`) is measured at runtime against the row's bounds (`PromoSection` reads `getBoundingClientRect()` for the row and each card via `viewChild`/`viewChildren`, inside an `afterRenderEffect`), and any card whose right edge would fall past the row's right edge gets `visibility: hidden` (not removed from the DOM, so hiding it doesn't shift the cards before it). A `ResizeObserver` on the row re-triggers this measurement whenever the available width changes, so the visible count grows on wider viewports and shrinks on narrower ones, always landing on whichever N cards fit *entirely* — never a partial sliver at the edge. This replaces an earlier CSS-overflow-only version of this decision, which relied on `overflow: hidden` alone to clip whatever didn't fit — that produced a partially-cut-off card at the boundary whenever the available width wasn't an exact multiple of (card width + gap), which is the common case. `ResizeObserver` is guarded with a `typeof ResizeObserver !== 'undefined'` check (absent in the Vitest/jsdom unit-test environment, where every card's measured rect is zero-sized anyway and so remains fully "visible" — the real fitting behavior is covered by e2e tests in a real browser instead).
- **Badge clipping fix**: the discount badge is positioned with a negative `top`/`right` offset so it pokes outside its card's own box (see `promo-card.css`). Because `.promo-row` clips overflow on all sides, not just horizontally, this negative offset was being clipped by the row's own top/right edge even for cards that otherwise fit entirely — not just cards deliberately cut off by width. Fixed by giving `.promo-row` enough `padding-top`/`padding-right` to cover the badge's maximum protrusion (including its rotation and pulse-animation scale), so only intentionally-overflowing cards get clipped, never a fully-fitting card's badge.
- **Animation**: the discount badge gets a CSS `@keyframes` pulse/glow, disabled via `@media (prefers-reduced-motion: reduce) { animation: none; }` while keeping its vivid background color — the same "no motion, but still not invisible" pattern already established for button press feedback elsewhere in the app.
- **Translations**: new keys for the section's headline and the discount badge text (e.g. `promoSection.headline`, `promoSection.discountBadge` with a `{percent}` placeholder); the add-to-cart control's accessible label reuses the existing `bookCard.addToCart` key rather than adding a duplicate, consistent with how `RecommendationCard` already reuses it.

## Risks / Trade-offs

- [Real books get a fabricated "-73% off!!" badge attached, which — divorced from the parody framing — could read as actually misleading rather than obviously tongue-in-cheek] → Accepted as the explicit point of the feature (confirmed intent: parody of aggressive ad patterns); mitigated somewhat by the deliberately garish, off-brand styling making it visually read as "this is a joke/ad," not a real storefront claim.
- [The JS-measured visible count briefly renders all candidate cards before `afterRenderEffect` runs and hides the non-fitting ones, which could show a one-frame flash of a partial card] → Accepted; `afterRenderEffect` runs in the `mixedReadWrite` phase after DOM update but before the browser paints in the common case, so this is not expected to be visually perceptible in practice; not worth the complexity of server-side/precomputed sizing for a satirical, non-critical section.
- [A curated query pool of ~10 AI-engineering terms will repeat across visits/no-results events, so "random" is visibly bounded rather than truly wide] → Accepted; a real random-book source doesn't exist to draw from, and a larger pool can be added later without changing the design.
