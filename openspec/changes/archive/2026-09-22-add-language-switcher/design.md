## Context

The app has no i18n mechanism today — every piece of UI text is a literal string baked into a template or built inline in a component (e.g. `cart-page.ts`'s `itemCountLabel` already picks between two hardcoded English words based on count; `book-card.ts`'s `formattedPrice`/`cart-page.ts`'s `formattedTotalPrice` already call `toLocaleString('de-DE', ...)`, hardcoded regardless of any language setting since none exists). All services in this app (`Cart`, `GoogleAuth`, `GoogleBooks`) use the `@Service()` decorator and are injected directly into components, which then read from them in templates (no pipes are used anywhere in this codebase). See proposal.md for why a header toggle rules out Angular's built-in (build-time, per-locale-bundle) i18n.

## Goals / Non-Goals

**Goals:**
- Instant, same-page language switching via a header control — no reload, no separate build per locale.
- Every static, app-authored piece of UI text is translated via a key→string dictionary, following the same direct-service-injection pattern already used throughout this codebase.
- Book search results (title, description, etc.) reflect the selected language too, by asking the Google Books API for that language's listings rather than translating text — see the dedicated decision below.
- Selected language persists across reloads (`localStorage`), defaulting to English on first visit.
- `<html lang>` reflects the current language; price/currency formatting follows it too (closing an existing inconsistency where `toLocaleString('de-DE', ...)` is hardcoded regardless of any setting).

**Non-Goals:**
- No machine translation of book data — instead, the Google Books API's own `langRestrict` parameter is used so search results (title, authors, publisher, dates, description) are whatever the API returns for that language (see the "Book search results reflect the selected language" decision below). No new external translation API/dependency.
- No third language, no language auto-detection from browser settings, no ICU plural-rule engine — just a flat key→string dictionary with simple `{placeholder}` substitution, matching this app's existing "no unnecessary dependencies" pattern (e.g. hand-rolled description truncation, hand-rolled currency formatting via `toLocaleString` rather than `CurrencyPipe`).
- Brand names / proper nouns stay fixed: "My-Book-Store", "PayPal", and the "v1.0" version string are not translated.

## Decisions

- **New `Language` service** (`src/app/language/language.ts`, `@Service()`, matching the existing service convention): holds `readonly current = signal<'en' | 'de'>(...).asReadonly()` (initial value read from `localStorage`, falling back to `'en'`), a `setLanguage(locale: Locale)` method (sets the value directly, persists to `localStorage`) — used by the select control's `(change)` handler, since a `<select>` reports the chosen value directly rather than "the other one" — a `translate(key, params?)` method doing dictionary lookup + simple `{name}` placeholder substitution, and a `readonly localeCode = computed(() => this.current() === 'de' ? 'de-DE' : 'en-US')` used by `formattedPrice`/`formattedTotalPrice` instead of their current hardcoded `'de-DE'`. A constructor `effect()` keeps `document.documentElement.lang` in sync with `current()`.
- **Translation dictionary** (`src/app/language/translations.ts`): a flat `Record<'en' | 'de', Record<string, string>>` keyed by dotted, component-scoped names (e.g. `bookSearch.pageTitle`, `cartPage.item`) — no external i18n library, no nested/ICU structure. The full key inventory (one entry per string identified in proposal.md's impact list) is the checklist in tasks.md.
- **Consumption pattern**: components `inject(Language)` and call `language.translate('some.key')` (or `language.translate('some.key', { page, total })` for the two interpolated cases) directly in templates — the same direct-injection-and-call pattern already used for `cart.count()`, `googleAuth.user()`, etc. No pipe is introduced, since none exists elsewhere in this codebase.
- **Pluralization stays component-owned**: `cartPage.item` / `cartPage.items` remain two separate keys, selected by the existing count-based ternary in `cart-page.ts` (already the established pattern) — German's invariant "Artikel" simply maps both keys to the same German string.
- **Language-switcher control placement and header layout**: the control is a new always-visible element (unlike `.cart`/`.login`, which are each conditionally shown based on auth state) between the cart icon and the user-info/login area. Today `.cart` and `.login` each independently carry `margin-inline-start: auto` to self-push right, since they're mutually exclusive (only one renders at a time). With an always-visible control between them, that no longer works cleanly (whichever auto-margined element renders first would leave an extra gap before the language selector). Fix: introduce a `.header-actions` wrapper (`display: flex; align-items: center; gap: ...; margin-inline-start: auto;`) around `.cart` + the new language selector + the user-info/login area, and remove the individual `margin-inline-start: auto` from `.cart` and `.login` — the wrapper pushes the whole cluster right as one unit; its children just flow normally inside it.
- **Revision — two-row header-actions layout**: `.header-actions` changes from a single flex row to `flex-direction: column; align-items: flex-end;`, holding two `.header-actions-row` children (each `display: flex; align-items: center; gap: ...`, the same gap the single row used to have): a top row containing only the language switcher, and a bottom row containing the cart icon, user-info/login-logout — matching a follow-up request to visually separate the language control from the rest of the header actions rather than have it inline with them. `align-items: flex-end` on the column right-aligns both rows to match the "top right" / "below" placement requested, without needing per-row margin tricks. Each moved element (`.cart`, `.language-switcher`, `.login`, `.logout`, `.user-name`) keeps its existing class and styling untouched — only the wrapping markup changed, so no other CSS needed updating.
- **Flag + code display, replacing the globe-icon toggle**: each language is shown as a flag emoji + language code as plain text (`🇬🇧 EN`, `🇩🇪 DE`) — flag emoji render natively with no icon library/SVG asset needed (same "no unnecessary dependencies" reasoning as elsewhere in this app), though rendering quality depends on the OS/browser's emoji font (e.g. Windows without a flag-glyph font shows a two-letter fallback box instead of a pictorial flag — same underlying character, a platform limitation, not an app bug). Originally implemented as a native `<select>` with two `<option>`s; superseded by a custom dropdown — see the revision below for why and what replaced it. The control's accessible name is the translated `header.languageSelector` key ("Language" / "Sprache"), describing the control generically rather than an action.
- **Currency/locale**: `book-card.ts`'s `formattedPrice` and `cart-page.ts`'s `formattedTotalPrice` switch from the hardcoded `'de-DE'` literal to `this.language.localeCode()`, so English shows "$"-free but comma/period-swapped formatting (e.g. "24.99 €" instead of "24,99 €") consistent with the selected language, while the currency itself stays EUR in both.
- **Book search results reflect the selected language via the Google Books API, not machine translation**: `GoogleBooks.search()` injects `Language` and adds `langRestrict: this.language.current()` to every request — the same `en`/`de` codes `Language` already uses are valid Google Books `langRestrict` values, so no mapping table is needed. This asks the API for listings *in* the selected language rather than translating the English listing's text; a German search can return a different edition (different title, publisher, description — even a different cover) than the English one for the "same" book, or no results at all if no German-language edition is cataloged. `BookSearch` gets a constructor `effect()` that reads `language.current()` and, if a search is currently active (`activeQuery()` non-empty, read via `untracked()` so it isn't itself a dependency), re-runs `fetchPage(this.page())` — reusing the existing pagination-fetch path rather than introducing a second fetch mechanism, and preserving the current page rather than resetting to page 1.
- **Cart items are snapshots, not re-fetched**: this matches the already-established precedent that `price` (and `averageRating`/`ratingsCount`) are fixed at add-time on the `BookSummary` copy `Cart.add()` stores — a book already in the cart keeps whatever title/description/price it had when added, regardless of later language changes. Re-fetching cart items would need a stable Google Books volume ID, which isn't stored today (out of scope here).
- **Revision — `color-scheme: dark` on `html`**: opening the `<select>`'s dropdown popup briefly flashed light-grey before repainting dark. Root cause: this app has a fixed dark theme (no light mode, no toggle), but never declared `color-scheme`, so the browser had no way to know that and defaulted native form-control chrome — most visibly a `<select>` popup's initial paint — to light. Added `color-scheme: dark` to `html` in `src/styles.css` (kept, still generally correct practice for a dark-only app — improves default native scrollbar/checkbox/etc. rendering too), but this alone did not fully resolve the flash — see the next revision.
- **Revision — native `<select>` replaced with a fully custom dropdown**: the flash persisted in Firefox after the `color-scheme` fix. Root cause: a `<select>`'s dropdown popup is rendered by the browser/OS as native UI outside the page's normal rendering pipeline, and `color-scheme` support for that popup is inconsistent across engines — Chromium themes it fully, but Firefox's native popup widget doesn't reliably honor it, so it can still paint with default (light) OS chrome before/without ever fully adopting the page's dark styling. Since this can't be reliably fixed from CSS for every engine, the `<select>` was replaced with a self-built dropdown: a `<button class="language-switcher-toggle">` showing the current flag + code, and, when open, a `<div class="language-switcher-menu" role="listbox">` of `<button role="option">` elements — an ordinary positioned `<div>` styled entirely by this app's own CSS, so there is no native popup involved at all and nothing left for the browser to paint with default chrome. `Header` holds `languageMenuOpen = signal(false)`, toggled by the button and closed on selection, Escape (`(keydown.escape)` on the wrapper), or a `@HostListener('document:click', ...)` that closes the menu when a click lands outside `ElementRef.nativeElement`. `Language.setLanguage(locale)` is unchanged from the select-based revision — only how the UI invokes it changed. Verified in both Chromium and Firefox (via `npx playwright install firefox`) that the menu now renders with the app's own dark styling immediately, no flash, since no native widget is ever created.

## Risks / Trade-offs

- [Existing unit tests (`header.spec.ts`, `book-search.spec.ts`, `book-card.spec.ts`, `cart-page.spec.ts`) assert on literal English strings] → Since `Language` defaults to English with no stored preference, and uses the same real-service-injection pattern the rest of the codebase's tests already rely on (not a mock), most existing assertions keep passing unchanged as long as `Language` is providable in each test's `TestBed` (it will be `@Service()`/root-provided, same as `Cart`/`GoogleAuth`, so no explicit provider is even required) — text assertions that queried a literal string like `'Search'` now go through translation but resolve to the same English string by default.
- [`localStorage` persists within a test file's shared jsdom `window` across multiple `it()` blocks] → If any test exercises `language.setLanguage(...)` or the header's language control, a later test in the same file could unexpectedly start in German unless `localStorage` is cleared between tests. Mitigate with a `beforeEach`/`afterEach` clearing the relevant key in any spec file that touches it.
- [The custom dropdown is now a hand-rolled widget instead of a native `<select>`, so this app is responsible for its own open/close and click-outside behavior rather than getting it for free from the browser] → Kept deliberately minimal: a signal for open/closed state, a document-click listener to close on an outside click, and an Escape-key handler — no focus-trapping or roving-tabindex arrow-key navigation, since the control only ever has two options and every element in it (`<button>`) is natively focusable/activatable via Tab and Enter/Space without extra JS. Accepted as proportionate to a two-item control, consistent with this app not implementing full ARIA widget patterns elsewhere either.
- [`header.css` (4.19 kB) exceeds the project's 4 kB `anyComponentStyle` warning budget in `angular.json` by 194 bytes, after the custom dropdown's styles were added] → A build warning, not an error (the error threshold is 8 kB); left as-is rather than trimming or restyling the stylesheet, since that would be scope beyond fixing the reported flash.
- [Two spec files (`book-search`, `shopping-cart`) needed MODIFIED requirements; most others didn't] → Verified precisely: only requirements that pin an *exact* English string as normative SHALL-level content needed changing. Requirements that describe a control generically (`google-login`, `app-header`, `app-footer`) don't conflict with translated implementation text, so they're intentionally left untouched — avoids inflating the spec deltas with changes that wouldn't actually alter any requirement's truth value.
- [`langRestrict` can return a different edition (different title/publisher/description, even a different cover) than the English listing for the "same" book, or zero results if no German-language edition is cataloged] → Accepted trade-off, explicitly named in the spec rather than hidden: it's the direct consequence of asking the real API for a different language instead of faking a translation. A no-results case falls through to the existing "Book not found" handling, not a new error state.
- [Changing the language while a search is in flight (loading) could produce a race between the in-flight response and the language-triggered re-fetch] → `fetchPage` already sets `state` to `'loading'` before each request; the effect calling it again simply starts a newer request over the same `state` signal. Playwright/RxJS `HttpClient` resolves each `subscribe()` independently, and the last `state.set(...)` to run wins — acceptable for this app's scope (same class of "last write wins" already implicit in the existing pagination code, not a new risk introduced here).
